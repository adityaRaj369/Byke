1. Executive Summary
Byke is a two-wheeler ride-hailing and errand/delivery platform connecting riders (bike/scooter owners) with users who need transportation, personal errand services, and parcel delivery. Unlike traditional platforms charging per-ride commissions, Byke operates on a flat monthly subscription of ₹500 per rider, giving them unlimited ride acceptance capacity and full platform feature access.

2. App Overview & Platform Architecture
Byke consists of three separate applications operating on a shared backend:

2.1 User App
Installed by customers. Allows booking rides, requesting errands, scheduling parcel deliveries, and tracking orders in real time.

2.3 Admin Dashboard (Web)
Used exclusively by the platform owner. Provides full visibility into all operations, user/rider management, complaint resolution, financials, and platform configuration.

3. User Registration, Login & Profile
3.1 Registration Flow (Users)
	•	User opens the app and enters their mobile number.
	•	System sends a 6-digit OTP via SMS.
	•	User enters OTP within 60 seconds (with resend option after 30 sec).
	•	On first login: user completes their profile — Name, optional profile photo.
	•	Subsequent logins: OTP only, profile auto-loads.

3.2 User Profile Data Stored
	•	Full name
	•	Mobile number (primary key / unique identifier)
	•	Profile photo (optional)
	•	Date of registration
	•	Total rides/errands booked
	•	Average rating given to riders
	•	Saved home/work addresses
	•	Preferred payment method
	•	Account status: Active / Suspended / Banned
	•	Complaint history
	•	Notification preferences

3.3 User Rating System
After every completed ride or errand, the user is prompted to rate the rider (1–5 stars + optional comment). This rating is averaged and displayed publicly on the rider's profile. Users can also be rated by riders for behavior (internal metric visible to admin only).
4. Rider Registration, Onboarding & Verification

	•	Admin reviews application, checks documents, approves or rejects.
	•	On approval, rider receives notification and can activate subscription.
	•	After payment of ₹500/month, rider is 'Active' and can receive rides.

4.3 Rider Subscription Model
Riders pay a flat ₹500/month to remain active on the platform. There is no per-ride commission deducted. Riders keep 100% of the fare they charge (fare is set by the platform, not negotiated).
	•	Payment is auto-renewed monthly via Razorpay/Stripe.
	•	Riders get a 3-day grace period if payment fails before suspension.
	•	Subscription can be paused (rider goes 'inactive') and resumed anytime.
	•	No refund for partial months.

4.4 Rider Status States
	•	Pending — Application submitted, awaiting admin review
	•	Approved / Active — Subscription paid, ready to receive rides
	•	Inactive — Subscription lapsed or voluntarily paused
	•	Suspended — Temporarily restricted by admin (with reason)
	•	Banned — Permanently removed from platform
	•	On Ride — Currently serving a booking
	•	Available — Online and accepting rides
	•	Offline — Not accepting rides (rider toggled offline)
5. Booking Types & Service Catalog
Byke supports three core service types under a single booking flow:

5.1 Ride Booking
The user requests a two-wheeler ride from Point A to Point B. The rider acts as a driver for the user (pillion ride).
	•	Pickup and drop location entered via map or search.
	•	Estimated fare shown before confirmation.
	•	Estimated time of arrival (ETA) shown.
	•	Rider navigates using in-app map to pickup, then to destination.

5.2 Errand Booking
The user asks the rider to complete a personal errand on their behalf. Examples include picking up groceries, collecting medicines, picking up dry cleaning, paying a bill, etc.
	•	User describes the task in a text box (free form + pre-set categories).
	•	User can attach a list or image (e.g., photo of a shopping list).
	•	User sets an estimated budget for purchases (if buying items).
	•	Option to add item-by-item shopping list within the app.
	•	User specifies pickup location (e.g., a market) and drop-off (home).
	•	Rider gets full errand instructions on their app.
	•	Rider can message/call user for clarifications.
	•	Cash advance for purchases: User can send money via UPI to rider before task.
	•	Rider marks items as 'collected' as they go (optional checklist).

5.3 Parcel Delivery
The user sends a parcel from one address to another using the rider as a courier.
	•	Sender address and recipient address entered.
	•	Parcel description entered (type, approximate weight).
	•	Recipient name and phone number entered.
	•	Recipient receives an SMS/notification with rider details and ETA.
	•	Rider picks up parcel, confirms via photo, and delivers.
	•	Delivery confirmation: Recipient OTP or photo proof at drop.
	•	Sender notified when parcel is picked up and when delivered.

5.4 Booking Flow (Common)
	•	User selects service type (Ride / Errand / Parcel).
	•	User fills in relevant details (locations, description, items).
	•	System calculates and shows fare estimate + ETA.
	•	User confirms booking.
	•	System broadcasts request to nearby available riders.
	•	First rider to accept gets the booking.
	•	User notified: 'Rider Found — [Name] is on the way'.
	•	Live tracking begins.
	•	Rider completes the task.
	•	Both parties rate each other.
	•	Booking marked Complete. Receipt generated.

5.5 Fare Estimation
Fares are calculated based on:
	•	Base fare (flat amount per booking type)
	•	Distance-based rate (per km)
	•	Time-based rate (per minute, for errands / waiting)
	•	Surge pricing during high-demand periods (admin configurable)
	•	Additional charges for parcel weight category (admin configurable)

8. Cancellation Policy
8.1 User Cancellation
	•	User can cancel at any time before rider arrives at pickup.
	•	Free cancellation within 2 minutes of booking.
	•	After 2 minutes: a cancellation fee may apply (admin configurable, e.g., ₹10–₹30).
	•	If user cancels after rider is en route, rider earns a partial compensation fee.
	•	3 cancellations in 24 hours: user receives a warning notification.
	•	Excessive cancellations may result in temporary booking restriction (admin decision).

8.2 Rider Cancellation
	•	Rider can cancel before reaching the pickup point.
	•	Cancellation reason is mandatory (pre-set options + free text).
	•	Cancelled booking is re-broadcasted to other available riders.
	•	Rider cancellation is logged. Repeated cancellations reduce rider's acceptance rate score.
	•	Admin can view rider cancellation history and take action if needed.
	•	Rider cannot cancel after pickup has been confirmed (booking is in progress).

8.3 Cancellation Reasons (Pre-set Options)
For Riders: Vehicle issue, Personal emergency, User not responding, Wrong location, Other
For Users: Changed plans, Wrong location entered, Taking too long, Found alternate transport, Other
9. Ratings & Reviews
9.1 Rating Flow
	•	After every completed booking, both user and rider are prompted to rate.
	•	Rating window: 24 hours after completion. After that, option expires.
	•	1–5 star rating required. Comment is optional.
	•	Rating is published immediately; comments are reviewed for abuse.

9.2 Rider Public Rating
	•	Displayed on rider profile (visible to users when booking).
	•	Calculated as rolling average of last 500 ratings (or all if fewer).
	•	Riders with average below 3.0 receive a warning from admin.
	•	Riders below 2.5 average may be suspended pending review.

9.3 User Internal Rating
	•	Users rated by riders (1–5 stars) — this is NOT publicly displayed.
	•	Visible to admin only; used to identify problematic users.
	•	Admin can flag or suspend users with consistently low rider ratings.

9.4 Review Moderation
	•	Abusive, offensive, or spam reviews can be reported.
	•	Admin can remove a review with a reason logged.
	•	Removed reviews do not count toward the average.

17. Rider Bidding System
Byke uses a competitive bidding model instead of auto-assigning rides at a fixed fare. When a user posts a booking request, nearby riders can view it and submit their price bid. The user then reviews all bids and selects the rider they prefer. This gives users pricing transparency and choice, while motivating riders to offer competitive and fair rates.

17.1 How Bidding Works — Full Flow
	•	User fills in booking details (service type, pickup, drop, errand description, etc.) and submits the request.
	•	System broadcasts the request to all available riders within the service radius.
	•	A bidding window opens — riders have 30 to 60 seconds (admin configurable) to place their bid.
	•	Each rider sees: booking type, pickup area, drop area, estimated distance, and the platform-set price range (min–max allowed bid).
	•	Rider enters their offered price (within the allowed range) and submits.
	•	User's app shows all incoming bids in real time as riders submit them.
	•	Each bid card displays: Rider name, profile photo, star rating, vehicle type, vehicle number, and bid amount.
	•	User reviews all bids and taps 'Accept' on their preferred rider.
	•	Accepted rider is notified immediately and navigation begins.
	•	All other bidding riders are notified that the booking was taken.

17.3 What the User Sees (Bid Selection Screen)
After submitting a booking, the user lands on the Bid Selection Screen which updates live as bids come in:
	•	Countdown timer showing how much bidding time remains
	•	List of all bids received, each showing:
	•	Rider photo and full name
	•	Star rating (e.g. ★ 4.7 — 312 rides)
	•	Vehicle type, make, and registration number
	•	Bid amount prominently displayed (e.g. ₹85)
	•	'Accept' button on each bid card
	•	Bids are sortable by: Lowest Price, Highest Rating, Nearest Rider
	•	User can tap any rider's name to view their full profile before deciding
	•	Once user taps Accept, booking is locked — no further bids shown

17.4 What the Rider Sees (Bidding Screen)
	•	Incoming booking alert with: service type, pickup area (neighbourhood, not exact address), drop area, and estimated distance
	•	Platform-set price range displayed (e.g. 'Bid between ₹50 – ₹150')
	•	Countdown timer showing time remaining to bid
	•	Numeric input to enter bid amount
	•	'Submit Bid' button — becomes 'Edit Bid' after first submission
	•	Rider can see if their bid was accepted or if booking was taken by another rider
	•	Exact user address is revealed only after bid is accepted

17.5 Admin Configuration for Bidding
	•	Set bidding window duration (30s / 45s / 60s) — global or per service type
	•	Set minimum and maximum bid per service type (ride, errand, parcel)
	•	Set distance bands with different min/max ranges (e.g. 0–3 km, 3–10 km, 10+ km)
	•	Toggle surge mode: temporarily raise max bid ceiling during peak hours
	•	View bid history per booking (which riders bid, amounts, who was selected)
	•	Monitor average accepted bid price to calibrate price ranges over time

17.6 Bidding — Edge Cases & Rules
	•	If a rider accepts a booking (bid accepted) and then cancels, their cancellation rate score is penalised more heavily since they actively chose that ride.
	•	Riders with account warnings or rating below 3.0 may be shown lower in the bid list (admin configurable ranking penalty).
	•	Users cannot collude with riders to accept inflated bids repeatedly — admin analytics can flag anomalous bid acceptance patterns.
	•	For parcel and errand bookings, the bid covers the rider's service fee only — purchase costs for errands are handled separately.
